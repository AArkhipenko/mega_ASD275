# Поток данных: от DWIN до ASD275

Полная цепочка: **буфер A (RX-кольцевой) → события → роутер → реестр → хранилище (latest-wins) → транслятор → драйвер (очередь 1+1) → RS485**. Раздел собран по разделам 2–4 [base-design.md](../sessions/base/artifacts/base-design.md) и разделу 3 [base-requirements.md](../sessions/base/artifacts/base-requirements.md); этап разработки не выполнен, поэтому ссылки — на планируемые файлы и целевые контракты (раздел 8 дизайна).

## 1. Буфер A: кольцевой RX-буфер DWIN (в data_source)

Целевой файл: `lib/dwin_lcm/*` (реальный DWIN), `lib/dwin_lcm_simulator/*` (симулятор).

- Размер: **128 байт** — порядка длины нескольких кадров DWIN (дизайн, раздел 2.1).
- Заполняется из прерывания UART; главный цикл только читает (FR-1).
- Политика переполнения: старые непрочитанные байты перезаписываются — **свежие данные важнее старых**.
- Разбор кадров — **в главном цикле**, неблокирующий: если кадр неполон, парсер выходит и цикл продолжается; при битом кадре парсер сбрасывается на поиск заголовка.
- Плюс периодическое чтение RAM DWIN по расписанию `millis()` (FR-2): частый полинг системных адресов (0x5002), редкий — настроечных (0x6000..0x6004) (R-2).

```
UART RX (прерывание) → кольцевой буфер [128 байт] → парсер в loop() → parameter_update{address, raw_value}
```

Событие — `struct parameter_update { uint16_t address; int32_t raw_value; }` (справочно, из кода: [include/data_source.h](../../include/data_source.h:12)).

## 2. Событие → роутер → реестр

- Роутер (`parameter_router`) — входная точка главного цикла. Целевой контракт: `handleEvent(address, raw)` — классификация через реестр + запись в хранилище; `processSystem()`, `processSettings()` (дизайн, раздел 8).
- Реестр (`parameter_registry`) — статический каталог дескрипторов `ParameterDescriptor{address, category, scale, unit, consumer}`; `find(address)` возвращает `nullptr` для неизвестного адреса (дизайн, раздел 8).
- **Неизвестный адрес**: отбрасывается с технической диагностикой в Serial, цикл не прерывается (FR-5; сценарий S6 приёмки).

## 3. Хранилище: latest-wins (буфер B)

- Целевой контракт (дизайн, раздел 8): `write(address, raw)` — запись с latest-wins и установкой флага «изменился»; `read(address, raw&)`; `hasChanged(address)`; `clearChanged(address)` — сброс флага потребителем после обработки.
- Одна запись на адрес из реестра: `{адрес uint16_t, значение int32_t raw, флаг uint8_t}`.
- Для **System**: значение замещается новым, про флаг — не критично (обработка в том же проходе).
- Для **Setting**: значение замещается, флаг «изменилась» устанавливается и ожидает применения по квоте (FR-8).

## 4. Транслятор: дельта → физические команды

- Целевой контракт (дизайн, раздел 8): `tick()` (конечный автомат движения), `setTargetAngle(float degrees)` (**re-targeting** — новая цель применяется немедленно, очереди целей нет, FR-9), `currentCommand()` → `DriverCommand`.
- Алгоритм для угла (FR-9..FR-11, дизайн раздел 4.4 приёмки S1/S2/S8):
  1. `delta = target − current` (в физических единицах: `raw × масштаб`).
  2. `|delta| < epsilon` → движения не требуется.
  3. Перевод дельты в обороты (по масштабу из реестра) и направление (знак дельты).
  4. Скорость — **считывается из хранилища в момент старта движения** и включается в команду старта; во время движения скорость не меняется (FR-10, решение владельца R-1).
- Настройки (скорость, масштаб) транслятор берёт из **локального кэша**, обновляемого по `on_settings_changed` от хранилища настроек — не перечитываются при каждом движении.

## 5. Драйвер: очередь 1+1 и RS485 (буфер C)

- Целевой контракт (дизайн, раздел 8): `sendCommand(const DriverCommand&)` — **не блокирует, ставит в очередь**; `isBusy()` — команда «в полёте»; `tick()` — обслуживание RS485 (RSE, таймауты, состояние).
- Очередь: **максимум 2 слота** — команда «в полёте» (выставлена по RS485, ждёт ответа/таймаута) и команда «на очереди» (последняя нормированная команда от транслятора). Новая команда **замещает** команду «на очереди» (latest-wins и здесь, дизайн раздел 2.3).
- Пока команда «в полёте», новые команды физически не выдаются; таймаут ответа по `millis()` порядка 100–200 мс → диагностика ошибки связи, команда снимается, очередь продолжает работать (дизайн раздел 2.3; приёмка S5).
- **Никогда не ставится в очередь «цель угла»**: цель живёт в хранилище (буфер B), драйвер получает только нормированное текущее действие (дизайн раздел 2.3).
- Пин RSE (D2) переключается под передачу/приём без блокирующего ожидания (FR-13).

## 6. RS485 → ASD275

- Последовательность Modbus для движения (целевая, из раздела 2/README; регистры — справочно из [lib/servo_driver/src/servo_driver.h](../../lib/servo_driver/src/servo_driver.h:29)): запись оборотов **0x202** → запись скорости **0x204** → старт/сброс **0x11F** = 1 → 0. Включение привода — **0xB5** (один раз при старте), состояние движения опрашивается чтением **0x1000**.
- Связь: Serial3, 9600 8N2; адрес привода по умолчанию 0x01.
- Ошибка связи (нет ответа до таймаута) — диагностическое/аварийное состояние, главный цикл не останавливается (FR-14).

## 7. Что происходит в главном цикле `loop()` (целевой, дизайн раздел 3)

Порядок шагов фиксирован и выражает приоритеты (FR-15..FR-17):

1. **Опрос источника данных**: полинг RAM DWIN по расписанию `millis()`; приём байт из кольцевого буфера.
2. **Разбор кадров DWIN** в события «адрес, значение» (без ожиданий).
3. **Обработка параметров системы (приоритет 1)**: каждое событие угла сразу пишется в хранилище и передаётся транслятору движения; новая цель применяется немедленно.
4. **Обработка настроек (приоритет 2)**: только если в этом проходе не было свежих системных параметров; дополнительно ограничена квотой — не чаще раза в N проходов (N = 10–20).
5. **Тик трансляторов** (`tick()`): конечный автомат движения, таймауты по `millis()`.
6. **Тик драйверов** (`tick()`): RS485 — переключение RSE, отправка команды из очереди, ожидание ответа с таймаутом.
7. **Периодическая диагностика** в Serial (9600).

Ни одна операция не блокируется: нет `delay()`, нет ожидания UART или RS485 (FR-17, AC-3). Задержка «приём системного параметра → обновлённая команда драйверу» — не более одного прохода главного цикла (NFR-1).

Диаграмма последовательности (целевая) — раздел 3.2 [README.md](../../README.md), стек вызовов — раздел 3.4.
